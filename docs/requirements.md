# 项目简述与需求

## 项目定位

FGO 游戏辅助桌面工具，通过本地 Agent 与 ADB 连接安卓设备或模拟器，采集玩家已拥有的从者信息、整理游戏图像素材、管理编队，并根据游戏当前战况提供建议。GUI 逐步接近游戏中的卡片浏览和编队体验。

项目暂用名 FGO Assistant。用户所述“turai”暂按 Tauri 理解，待确认。

## 已提出的需求

| 编号 | 功能 | 基本要求 |
| --- | --- | --- |
| F01 | 从者档案 | 识别已拥有从者的身份、等级、宝具等级、再临阶段和技能等级，保存到本地数据库 |
| F02 | 游戏素材 | 从游戏头像与立绘中抓取缩略图，作为档案和编队操作素材 |
| F03 | 编队管理 | 自定义编队，包含概念礼装、御主礼装、助战及 COST 校验；可关联关卡，也可独立保存 |
| F04 | 战况辅助 | 本地 Agent 识别当前战况并给出建议 |
| F05 | 桌面 GUI | 查看从者、设置编队，逐步优化为接近游戏的操作体验 |
| F06 | 安卓连接 | 通过 ADB 支持模拟器或连接的安卓设备 |

## 首版范围与实现建议

首版目标已确认为 Windows/macOS + MuMu + FGO 国服；两种桌面系统分别验证 ADB 连接和安装包。形成“连接设备 → 截图 → 识别/校对 → 保存档案与素材 → 编队 → 战况建议”的完整链路。

首版已确认以玩家手动切页后触发识别为基础。自动翻页是低成本时可加入的可选增强，需先验证导航可靠性，不作为首版交付前提。战斗范围已确认为仅提供建议，由玩家手动操作；首版不包含战斗点击执行。本地编队保存与在游戏内自动配置队伍是两个不同功能，后者尚未确定。

建议首版支持手工录入和修正，以便识别尚不完整时仍能使用。未知字段保持未知，不用 0 代替。

## 业务规则

- 同一图鉴从者可能有多份持有实例，不能按名称或头像直接合并。
- 同一从者的不同再临、灵衣图像可能不同；视觉外观不能直接推断实际再临阶段。
- 低置信度、缺字段或跨页面身份无法确认时进入待校对；不得覆盖已确认数据。
- 未扫描到的从者不能因此被判定为已删除。数据带采集时间和来源。
- 编队与玩家持有实例关联；助战是单独的来源类型，不伪装成玩家持有从者。
- 首版建议按常规六槽位展示，三前排、三后备；关卡限制交给规则配置，特殊模式不硬套普通规则。
- 关卡绑定建议采用多对多：一套队伍可用于多个关卡，一个关卡可保存多套队伍。
- Agent 应说明建议依据、状态时间及未知信息；无法识别时明确返回信息不足。

## 首版验收草案

| 场景 | 可验证结果 |
| --- | --- |
| 设备连接 | 明确选定设备；无设备、未授权、离线时显示可操作的错误 |
| 档案采集 | 通过约定样本集识别基础字段；预览后保存，重启后仍可读取 |
| 校对 | 字段可修改；再次识别不静默覆盖人工确认值 |
| 重复持有 | 同名两份从者可独立保存；重扫产生合并候选而非直接新增或合并 |
| 名称校准与素材修正 | 识别名字后匹配中／日官方名称；歧义可重识别/手动校准，游戏截图素材可重新裁剪；换外观不误改培养数据 |
| 图像素材 | 缩略图与档案关联并可显示；缺失时显示占位图 |
| 编队 | 可创建、编辑、复制和保存；可无关卡保存，也可关联或解除关卡 |
| 编队完整性 | 概念礼装绑定到槽位、御主礼装绑定到队伍；助战单独配置，保存后可恢复 |
| COST 校验 | 显示各项费用和上限；覆盖恰好达限、超限、助战免计费与数据缺失；未知费用不按 0 处理 |
| 战况建议 | 对已支持的战斗截图返回状态摘要、建议和依据；未知页面不虚构状态 |
| 中断恢复 | 断连和取消不提交半份档案；已保存档案和编队不丢失 |

识别准确率、响应时间和支持分辨率在拿到代表性设备样本后制定；当前不承诺未经验证的指标。

## 待讨论问题

1. Windows/macOS 的版本、CPU 架构及 MuMu 版本是什么？两平台均为首版目标。
2. 优先接入哪个已有 Agent（piagent 或 Codex）？需核实具体 CLI 版本、图像输入及结构化输出接口。
3. 已确认仅给战斗建议、玩家手动操作；云端 API 可考虑支持，具体提供方待定。
4. 自动翻页的实际实现成本与支持页面范围，在 MuMu 样本验证后评估。
5. 编队是否要写回游戏？当前仅规划本地保存；概念礼装、御主礼装、助战和 COST 校验已纳入首版。
6. 从者字段是否扩展到附加技能、羁绊、芙芙、圣杯、硬币等？
7. 是否需要多账号、跨区服、备份导入导出？
8. 官方中／日名称资料的可靠来源与更新方式待确定；不引入官方头像比对。COST 等所需规则数据单独维护，具体来源另行确定。

已确认：接入本地已有 Agent，避免内建 Agent 框架。后续优先讨论具体 Agent 版本、名称资料来源与扩展培养字段。

## 首轮确认（2026-10-15）

- 平台：Windows 与 macOS；模拟器：MuMu；游戏：国服。
- 战斗：识别状态、给出建议，由玩家手动操作。
- Agent：优先接入本地已有 piagent/Codex，不内建 Agent 框架；可考虑直接调用云端 API。

## 第二轮确认（2026-10-15）

- 采集：接受手工切页后识别；自动翻页若实现成本低可加入，先评估，不阻塞基础功能。
- 编队：概念礼装、御主礼装、助战、COST 校验统一纳入首版。
- 实现建议：先支持礼装与御主礼装的本地条目选择、持有状态手工录入及修正；其批量自动识别尚未承诺。

## 第三轮确认（2026-10-15）

曾讨论公开图鉴与多外观候选方案，现由第四轮决定替代，不再作为实现范围。

## 第四轮确认（2026-10-15，当前方案）

仅保存官方从者中／日名称资料，用游戏中识别的名字比对校准；不做官方头像比对。头像和立绘使用游戏截图，提供重新识别、手工校准及重新裁剪替换入口。名字缺失或有歧义时保留未知，不以外观猜测。详见 [名称校准与识别评估](recognition-evaluation.md)。

实现建议：COST、礼装和御主礼装功能继续保留，所需费用、等级上限及资料先通过游戏可见信息识别/手工录入维护，来源与版本单独记录；当前不依赖下载完整官方图鉴。未知数据明确提示，不伪造技能效果或费用。
